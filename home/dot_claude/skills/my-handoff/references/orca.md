# Orcaへの引き継ぎ

`my-handoff orca` は独立したトップレベルのセッションに担当を移す。通常のサブエージェント起動や会話のforkは使わない。

## 起動条件を決める

- 既定は別ワークスペース。独立した話題はリポジトリの既定ブランチから開始する。現在の変更が必要な作業なら `--base-branch HEAD` を指定する。これは会話に基づいて親が決め、ブランチ名や作成の確認はしない。
- 新規ワークスペースには未コミット変更が移らない。依頼がその変更に依存する場合、起動前に解決する。同じファイルを読む調査なら別タブで扱える。複数セッションによる同じファイルの並行編集は割り当てない。
- ユーザーが同じワークスペースの別タブを指定したら `--tab` を付ける。作業ファイルが共有されることを依頼文に明記する。
- エージェントは指定を優先し、指定がなければ現在と同じ `codex` または `claude` を使う。スクリプトはモデル名や権限迂回フラグを追加しない。別タブの起動にはOrcaの既定の起動引数が適用されるが、UIで選んだモデル・推論量・アカウントがすべて引き継がれるとは限らない。モデル等の個別指定がある場合だけ `orca skills get orca-cli` の該当手順を確認し、指定を黙って捨てない。

## 親が実行すること

関連情報は `SKILL.md` の範囲だけでまとめ、次のスクリプトへ標準入力で渡す。引用付きheredocで改行、引用符、バッククォート、`$()`をそのまま渡す。依頼文中に同じ区切り行がないことを確認する。

```bash
bash "$HOME/.claude/skills/my-handoff/scripts/launch-orca-handoff.sh" \
  --name handoff-topic --agent codex <<'HANDOFF_BRIEF'
## 依頼と完了条件
対象の話題についての具体的な依頼と、完了を判定する条件。

## 方針・制約
会話にしかない判断と理由。許可された操作の範囲。

## 着手箇所と担当範囲
最初に見るファイル、次の作業、元のセッションに残す担当。
HANDOFF_BRIEF
```

- 同じワークスペースの別タブ: 上の呼び出しに `--tab` を付ける。
- 現在のコミットに基づく別ワークスペース: `--base-branch HEAD` を付ける。未コミット変更がある場合はエラーになる。
- 明示された別の分岐元: `--base-branch <ref>` を付ける。
- スクリプトは現在のGit作業場所を明示してOrcaを呼び、ワークスペース作成・端末起動・依頼送信を行う。新規ワークスペース名には短い識別子を自動で付け、同じ話題の再依頼でも別のブランチを作る。公開・commit・pushは行わない。

親はOrcaのコマンド一覧や生のJSON、起動した端末の全文を読まない。スクリプトの短い結果だけで移動先と送信状況を報告し、引き継ぎ文を最終回答に再掲しない。新規ワークスペースでは依頼文付きの起動要求、別タブでは準備完了後の入力の受け付けまでを確認する。作業の着手・完了や認証の成功までは保証しない。

## エラー時

スクリプトが失敗したら原因と作成済みの場所を報告する。作成・送信を自動で再実行しない。結果不明のタイムアウトでは、既に作成・送信済みの可能性がある。ワークスペースや端末を列挙して状態を確認し、重複起動・二重送信を避ける。作成済みのワークスペースを自動削除しない。

親が後から進捗を取り込む仕組み、定期確認、引き継ぎ台帳は作らない。

## スキル変更時の検証

適用後に `node --test "$HOME/.claude/skills/my-handoff/scripts/launch-orca-handoff.test.mjs"` を実行する。通常の引き継ぎでは実行しない。
