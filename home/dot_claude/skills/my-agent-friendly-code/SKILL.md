# エージェントが扱いやすいコード

エージェントが検索して読むソーステキストだけで、コードの意図を追えるように書く。最初の検索で
目的の定義にたどり着き、安全に変更できるだけの周辺情報をその場で得られる状態を目指す。
人間にとっての読みやすさを保ち、エージェント向けという理由で儀式的な構造や不要な変更を加えない。

## 既存コードの尊重

1. 編集対象と、最も近い呼び出し元、契約、テストを読む。
2. 修正対象の不具合を生んでいない限り、既存のドメイン用語、命名規則、ディレクトリ構成に従う。
3. この指針は、新規作成する箇所と大きく変更する箇所に適用する。無関係なコードを、エージェントが
   読みやすいという理由だけで改名、移動、整形しない。
4. 依頼された動作を明示できる最小の実装を選ぶ。将来使うかもしれないという理由で抽象化を加えない。

## 検索の手掛かりになる命名

- 公開する関数、型、クラス、定数、設定キーには、対象のドメインが分かる語を入れる。リポジトリ内に
  複数のクライアントがあり得るなら、`createClient`より`createStripeClient`を選ぶ。
- 処理には、動作と対象が分かる名前を付ける。`process`より`calculateInvoiceTotal`、`loadData`より
  `loadWorkspaceSettings`を選ぶ。
- コード、パス、テスト、スキーマ、文書を通して、一つの概念には一つの用語を使う。同じ概念を同義語や
  説明のない略語で呼び分けない。
- 値の取り違えが現実的な不具合になり得る場合は、意味の異なる基本値に別の型を与える。単なる二つの
  文字列ではなく、`UserId`と`OrganizationId`を使う。
- 意味がその場で分かる短い局所スコープでは、短い名前を使ってよい。すべての識別子をリポジトリ全体で
  一意にするためだけに、ループ変数や非公開ヘルパーの名前を長くしない。
- モジュール名や型名だけでドメインを特定できない場合、`data`、`item`、`info`、`config`、`manager`、
  `processor`、`handler`、`helper`、`util`のような汎用名を公開識別子に使わない。
- 公開識別子を追加または改名する前に、候補名をリポジトリ内で検索する。無関係な一致が大半を占める
  場合は、その名前を受け入れず、不足しているドメイン語を加える。

## 所有範囲と役割が分かるパス

- ディレクトリ名でドメインや機能を示し、ファイル名で責務を示す。`utils/calculation`より
  `billing/invoice-total`、`services/client`より`payments/stripe-client`を選ぶ。
- 言語とプロジェクトの規約が許す場合、主要な定義とファイル名を対応させる。
- 新しいコードは、その動作を所有する既存ディレクトリのうち最も狭い場所へ置く。別の分類方法を
  並立させない。
- `common`、`shared`、`helpers`、`utils`を既定の置き場所にしない。複数ドメインで共有する契約が
  実際にあり、リポジトリでもその場所を正本として扱っている場合だけ使う。
- 密接に関係する実装、型、テストは、パスまたは識別子の検索で必要な作業範囲が見える距離に置く。
  単独で意味を持つ境界がないのに、一つの変更を複数ファイルへ分散させない。
- 一ファイル一定義を強制しない。一つの動作を理解するために移動が必要な断片群より、まとまりのある
  完結したファイルを選ぶ。

## 局所的で明示的な処理

- 公開シグネチャだけで、入力、出力、失敗時の動作が分かるようにする。実装を読まなければ契約が
  分からない状態を避ける。
- 信頼できないデータは境界で解析し、検証する。内部では、緩いマップ、文字列、`any`相当の値を何度も
  解釈せず、意味が明示されたドメイン値を渡す。
- 不正な組み合わせを防げる場合や網羅的な処理が必要な場合は、状態遷移と許可された種類を
  プロジェクトの型機能で直接表す。
- 設計上問題がなければ、多段の再エクスポート、依存先を暗黙に探す仕組み、暗黙のグローバル状態、
  文字列による実行時検索より、直接のインポートと名前付きの依存関係を選ぶ。
- 対応表が小さく、機能の変更に合わせて更新される場合は、規約だけに依存する登録やリフレクションより
  明示的な対応表を選ぶ。フレームワークが動的登録を要求する場合は、検索できるドメイン名を登録箇所に置く。
- 副作用は関数やモジュールの境界で分かるようにする。純粋な計算や単純な参照に見える名前の裏で、
  入出力や状態変更を隠さない。
- 短い式が業務ルールを隠す場合は、素直な分岐と意味のある中間変数を使う。明白な処理まで冗長に
  書き広げない。
- 正本となる既存実装を再利用する。検索しやすさや局所性を理由に処理を複製しない。

## 検索先に置く補足情報

- 契約、不変条件、副作用、分かりにくい理由を名前と型だけで表せない場合は、定義の直上に短いコメントや
  docstringを置く。
- 意外な制約が存在する理由を書く。実装を読めば分かる動作を言い換えない。
- エラーメッセージには、失敗した操作と対象のドメインオブジェクトを特定できる情報を含める。
  プロジェクトの規約に従い、原因となったエラーを保持する。
- 関連する定数、既定値、検証規則は、それを所有する定義の近くに置く。共有契約として別の正本が
  必要な場合だけ分離する。

## 変更箇所の確認

実装を終える前に、次を確認する。

- 依頼に含まれるドメイン語で検索すると、無関係な結果に埋もれず、変更ファイルと主要な定義が見つかる。
- 新しい公開識別子から、その利用範囲で必要なドメインと責務が分かる。
- 新しいパスから、ファイルを開かなくても所有範囲と役割が分かる。
- 変更を理解するために、別名、多段の再エクスポート、動的登録、汎用ヘルパーモジュールを不要に
  たどる必要がない。
- シグネチャと型が契約を表し、コメントはコードだけでは表せない情報に限られている。
- 形式を整えるためだけの無関係な改名、移動、抽象化、複製を加えていない。
